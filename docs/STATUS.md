# Status de implementação — ZENITH FLOW

Última atualização: 2026-09-05.

## Implementado

- Monorepo (npm workspaces): `apps/web` (Next.js 14 + Tailwind), `packages/ui` (design system) e `packages/db` (Prisma + Postgres).
- **Sidebar de navegação** completa (`packages/ui/src/navigation`):
  - Todas as abas do manual (Visão geral, Produção, Gestão, Inteligência e automação, Comunicação e recursos, Sistema) cadastradas em `nav-config.ts`.
  - Recolhida por padrão (68px), expande por hover, foco de teclado ou clique no botão de fixar; delay de 200ms ao recolher.
  - Submenu abre apenas por clique/teclado (Clientes, Operação, Conteúdo, Financeiro, Pessoas, Configurações).
  - Tooltip acessível no estado recolhido (400ms), `aria-current="page"` no item ativo, `aria-expanded`/`aria-controls` nos submenus.
  - Preferência de fixação (`pinned`) persistida em `localStorage`. Respeita `prefers-reduced-motion`.
  - `MobileDrawer` (<768px) com focus trap, fechamento por Escape/backdrop/botão.
  - Agora exibe dados reais de sessão (nome, papel, agência) e um botão funcional de "Sair".
- **Release 1A — Auth, agência, workspace, membros, RBAC** (banco real, Neon Postgres em `sa-east-1`):
  - `packages/db`: schema Prisma (`User`, `Session`, `Account`, `Verification` do Better Auth + `Agency`, `Workspace`, `Membership`, `AuditLog` do domínio ZENITH FLOW). Migrations aplicadas.
  - Auth por e-mail/senha via **Better Auth** (`apps/web/lib/auth.ts`), cookies HttpOnly, middleware protegendo todas as rotas exceto `/login`, `/signup`, `/convite/*`, `/api/auth/*`.
  - `/signup`: cria usuário + agência + workspace interno (kind `AGENCY`) + membership `AGENCY_ADMIN` numa única transação. `/login`. `/nova-agencia`: fallback para usuário autenticado sem agência.
  - `/configuracoes/equipe`: lista membros do workspace e (para `AGENCY_ADMIN`/`SUPER_ADMIN`) convida novos membros — gera link de convite com token (`/convite/[token]`), já que envio de e-mail real é Fase 2.
  - RBAC inicial em `apps/web/lib/rbac.ts` (8 papéis do manual, seção 7.1); `canManageTeam()` guarda a ação de convidar.
  - Toda mutação relevante grava `AuditLog` (`agency.created`, `membership.invited`, `membership.accepted`).
  - Testado ponta a ponta via Playwright: signup → agência criada → sidebar com dados reais → convite → aceite por outro usuário → ambos "Ativo" na lista → logout. Dados de teste limpos do banco depois.
- **Release 1B (parte 1) — Clientes, contatos, onboarding** (seções 10 e 11 do manual):

  - Template de onboarding padrão (4 itens) semeado automaticamente para cada agência nova, no mesmo transaction do signup.
  - `/clientes/carteira`: lista clientes da agência + criação rápida (nome + documento).
  - `/clientes/[id]`: visão 360 — contatos (com contato principal), ações de mudança de status (`prospect → onboarding → ativo → pausado/em encerramento → encerrado → reativado`, seção 10), checklist de onboarding e timeline (histórico de status + notas, mesclados por data).
  - Checklist de onboarding: dependência **sequencial por ordem** (item N só libera após N-1 concluído) — simplificação deliberada do "grafo de dependências" do manual, documentada em `docs/DECISIONS.md`.
  - Ativar um cliente (`ATIVO`) cria automaticamente seu `Workspace` (kind `CLIENT`) — ainda sem membership/portal (Release 1D).
  - Testado ponta a ponta via Playwright: criar cliente → adicionar contato → iniciar onboarding → concluir item 1 → item 2 desbloqueia → nota na timeline. Dados de teste limpos do banco depois.
  - **Cadastro completo via popup**: `Modal` acessível (focus trap, Escape, backdrop) em `packages/ui`, reaproveitado por `ClientFormModal` (criação e edição). Campos: nome fantasia (único obrigatório), CNPJ, e-mail, telefone, WhatsApp e — só na criação — responsável (nome/e-mail/telefone), que vira automaticamente o contato principal. Botão "Editar dados" no perfil do cliente permite completar/corrigir a qualquer momento (`PATCH /api/clients/:id`) — cadastro parcial (só o nome) é o caso normal, não um erro.

- **Release 1C (parte 2) — Projetos e Tarefas** (seção 14 do manual):
  - `packages/db`: `Project` (pertence a cliente ou à agência), `Task`, `TaskStatusHistory` (append-only). Estado único `WorkItemStatus` compartilhado por projeto e tarefa: `backlog → planejada → em andamento → bloqueada → revisão → concluída/cancelada`.
  - `/operacao/projetos`: lista de projetos + popup de criação (nome, cliente opcional).
  - `/operacao/projetos/[id]`: quadro por status (colunas), mover tarefa por botão — **acessível, sem drag-and-drop** nesta fatia (ver `docs/DECISIONS.md`). Popup de nova tarefa com bloqueio opcional por outra tarefa do mesmo projeto.
  - `/operacao/tarefas`: lista de todas as tarefas da agência (com projeto e cliente).
  - **Bloqueio por dependência funciona de verdade**: uma tarefa com `blockedByTaskId` não pode ir para "Em andamento" ou "Concluída" enquanto a bloqueadora não estiver concluída — os botões ficam desabilitados e a API rejeita a tentativa (409). Dependência é bloqueio único (não um grafo), mesma simplificação pragmática do checklist de onboarding.
  - **Fecha o loop "demanda vira tarefa"**: demanda `APROVADA` ganha o botão "Converter em tarefa" (`POST /api/requests/:id/convert`) — escolhe projeto existente ou cria um novo, gera a `Task`, marca a demanda como `CONVERTIDA` e deixa um link direto pro projeto. Tudo numa transação só.
  - Testado ponta a ponta via Playwright: projeto manual com duas tarefas (uma bloqueando a outra) → tarefa bloqueadora percorre o quadro até "Concluída" → aviso de bloqueio some e o botão da outra tarefa libera. E também: demanda → triagem → aprovação → "Converter em tarefa" → projeto novo criado com a tarefa → demanda mostra "Convertida" com link. Dados de teste limpos do banco depois.
- **Release 1C (parte 3) — Rotinas recorrentes** (seção 15 do manual):
  - `packages/db`: `RoutineTemplate` (nome, cliente opcional, dia do mês, status `rascunho/ativo/pausado/arquivado`), `RoutineTemplateTask` (tarefas que se repetem), `RoutineRun` (uma linha por período gerado).
  - **`@@unique([templateId, period])` é a chave de idempotência de verdade** (não só uma checagem em código) — seção 15: "idempotency key impede duplicidade por rotina+período". Testei clicando "Gerar agora" duas vezes seguidas: só uma geração existe, a segunda tentativa volta como "já gerado" sem duplicar nada.
  - Só recorrência **mensal** (dia fixo do mês) nesta fatia — semanal e "dias úteis" ficam para quando houver caso real pedindo (documentado em `docs/DECISIONS.md`).
  - Gatilho é manual (botão "Gerar agora") por enquanto — em produção seria um worker agendado rodando a mesma função todo dia; a idempotência é idêntica nos dois casos, só muda quem aperta o play.
  - Ativar rotina → cria `Project` novo a cada geração (nome com o período, ex.: "Rotina mensal de conteúdo · Setembro de 2026") com as tarefas do template clonadas. **Pausar não apaga gerações passadas** (seção 15) — só bloqueia novas.
  - `/operacao/rotinas`: lista + popup de criação (nome, cliente, dia do mês, lista dinâmica de tarefas). `/operacao/rotinas/[id]`: tarefas do template, histórico de gerações (com link pro projeto criado), ativar/pausar/gerar.
  - Testado ponta a ponta via Playwright: criar rotina em rascunho ("Gerar agora" corretamente escondido) → ativar → gerar (projeto criado) → gerar de novo → mensagem de idempotência, sem duplicar. Dados de teste limpos do banco depois.

- **Release 1D (parte 6) — Solicitações no Portal + fechamento de um gap de segurança**: `/portal/solicitacoes` — cliente abre uma Demanda pra si mesmo (`POST /api/portal/requests`), sem escolher cliente (é sempre o próprio) nem prioridade (definida na triagem, seção 13). `requesterName`/`requestedByUserId` gravam o usuário real do portal — a demanda aparece no inbox interno (`/operacao/demandas`) normalmente, seguindo o mesmo fluxo de triagem/aprovação/conversão já existente. Lógica de criação extraída pra `lib/requests-create.ts`, compartilhada com a rota interna.
  - **Auditoria de segurança disparada por esta fatia**: como o Portal agora cria sessões autenticadas reais para clientes, toda rota interna que só checava `membership.agencyId` (sem checar o papel) ficou exposta — um cliente logado poderia, em teoria, chamar `/api/content`, `/api/requests/:id/status`, `/api/tasks/:id/assign` etc. diretamente e mexer em dados de qualquer cliente da agência, não só o seu. Antes do Portal existir isso não era um risco real (não havia sessão de cliente possível). Auditadas e corrigidas as **32 rotas internas** que faziam esse padrão — todas agora rejeitam papel de cliente com 403 antes de qualquer leitura/escrita (`isClientRole(membership.role)` logo após resolver o membership). Confirmado via Playwright: sessão de cliente chamando `POST /api/requests` e `POST /api/content` diretamente recebe 403 nos dois casos.

- **Release 1D (parte 7) — Comunicação e comentários (seção 19)**: substitui os comentários isolados de Conteúdo e Demandas (`ContentComment`, `RequestComment`, cada um preso ao seu módulo) por um sistema único e genérico — `CommentThread`/`Comment`/`CommentEdit`/`CommentMention` — reaproveitável por qualquer entidade futura sem coluna nova.

Só o autor edita/remove o próprio comentário.
  - **Menções por seletor, não por parsing de texto**: em vez de tentar reconhecer `@Fulano` dentro do texto livre (ambíguo com nomes compostos), a UI mostra chips clicáveis com os membros da equipe — a lista que vira `CommentMention` já vem estruturada, sem depender de regex.   - `apps/web/app/_components/CommentThreadPanel.tsx` é o componente único usado em `/conteudo/[id]` e `/operacao/demandas/[id]` — qualquer entidade nova (tarefa, projeto etc.) pode reaproveitar sem código extra, só passando `entityType`/`entityId`.
  - Testado via Playwright: comentar com menção, editar (marca "editado"), resolver/reabrir a thread, remover (vira tombstone), e um segundo usuário comentando com o nome de autor correto — em dois módulos diferentes (Demandas e Conteúdo) provando que o componente é genérico de verdade. Novo teste de isolamento em `packages/db` (4 testes: isolamento entre agências, unicidade de thread por entidade, histórico de edição/tombstone, resolução).   - **Envio real de e-mail foi explicitamente adiado por decisão do usuário** (perguntei via `AskUserQuestion` — Resend, SMTP existente, SendGrid ou pular — usuário escolheu pular): "Enviar" transiciona a campanha pra `ENVIADA` e cada destinatário ganha um link público (`/pesquisa/[token]`) copiável na tela, em vez de um e-mail disparado automaticamente. O ponto de plugue para um provedor real fica isolado nessa única rota (`POST /api/nps/campaigns/:id/send`) — trocar por envio de verdade não exige tocar em nenhuma outra parte do fluxo.
  - **"Público" resolvido por cliente, respeitando opt-out**: escolher clientes na criação da campanha gera um `SurveyRecipient` por cliente, usando o contato principal (ou o primeiro com e-mail) que não tenha `ClientContact.marketingOptOut` — campo novo, implementa literalmente "contatos com opt-out não recebem marketing" (seção 32.3). Cliente sem contato elegível é reportado, não trava a campanha inteira.
  - **NPS = % promotores − % detratores** (`apps/web/lib/nps.ts`), classificação padrão de mercado (9-10 promotor, 7-8 neutro, 0-6 detrator — o manual não redefine esses cortes). `NpsSnapshot` append-only, mesmo padrão de Health Score/Risco de churn — "Recalcular NPS" grava um novo snapshot a cada clique, nunca sobrescreve o anterior.
  - **eNPS deliberadamente fora de escopo desta fatia**: o próprio manual (seção 32.1) trata eNPS como "separado, acesso restrito, sem expor respondente quando anonimato for prometido" — um requisito de sensibilidade diferente do NPS de cliente. Misturar os dois no mesmo modelo seria errado; eNPS fica como pendência clara para quando houver tempo de tratar anonimato de verdade.
  - **Bug real de prioridade de mensagem, achado só ao testar o fluxo completo**: a página pública `/pesquisa/[token]` checava "campanha encerrada" antes de "você já respondeu" — alguém que respondeu e depois a campanha foi encerrada via "Você já respondeu esta pesquisa" agora tinha prioridade invertida, mostrando "Pesquisa encerrada" em vez da confirmação. Corrigido invertendo a ordem de checagem (quem já respondeu sempre vê a confirmação, independente do status atual da campanha).
  - Testado via Playwright: 3 clientes ativos com contato, campanha criada e editada em rascunho, enviada (destinatários viram "Enviado" com link copiável), cada um respondendo pelo link público (2 promotores nota 10/9, 1 detrator nota 2), recalcular mostrando NPS = 33 com Promotores: 2/Detratores: 1 (conferido contra o cálculo manual), encerrar campanha, e confirmação de que quem já respondeu continua vendo "obrigado" mesmo com a campanha encerrada. Novo teste de isolamento em `packages/db` (3 testes: isolamento entre agências, `@@unique` campanha+cliente, cálculo do NPS). Suite completa: 9 (Sidebar) + 46 (`packages/db`) = 55/55 passando.
- **eNPS** (seção 32.1 do manual, quinta fatia da Fase 2): `EnpsCampaign`, `EnpsInvite`, `EnpsResponse`, `EnpsSnapshot` — item de nav "eNPS" (`/pessoas/enps`) que já existia como `comingSoon: true` desde a Release 1E.
  - **Acesso restrito de verdade** (seção 32.1: "eNPS é separado e acesso é restrito"): `canViewEnps()` em `lib/rbac.ts` libera só `SUPER_ADMIN`/`AGENCY_ADMIN`/`HR` — qualquer outro papel interno (Gestor, Analista, Financeiro) é redirecionado ao tentar acessar `/pessoas/enps`, e as rotas de API rejeitam com 403.
  - **Anonimato implementado no desenho do schema, não só como regra de UI** — esta é a diferença estrutural do NPS de clientes: `EnpsInvite` rastreia só participação (convidado/enviado/respondido), nunca a nota; `EnpsResponse` não tem nenhuma coluna que aponte de volta pra quem respondeu (sem `employeeId`, sem `inviteId`) — uma resposta só prova "alguém convidado respondeu", nunca quem, mesmo para quem tem acesso direto ao banco. O respond (`POST /api/public/enps/:token/respond`) grava as duas informações (resposta anônima + participação do convite) como duas escritas na mesma transação, sem nunca ligar uma à outra.
  - Reaproveita a mesma matemática do NPS de clientes (`computeNpsBreakdown`, exportado de `lib/nps.ts` como `computeEnpsBreakdown`) — % promotores − % detratores, sem duplicar a fórmula.

  - Testado via Playwright: 3 pessoas criadas, campanha com 3 convidados enviada, cada uma respondendo pelo link anônimo (2 promotores nota 10/9, 1 detrator nota 1), recalcular mostrando eNPS = 33 (Promotores: 2/Detratores: 1), e **confirmação direta no banco de que nenhuma linha de `EnpsResponse` tem `employeeId`/`inviteId`** — não é só a UI que esconde, o dado nem existe. Bug real de teste encontrado no caminho (não do produto): e-mail gerado a partir de nome com acento ("Funcionário") quebrava a validação nativa do `<input type="email">` e travava o clique de cadastro silenciosamente. Novo teste de isolamento em `packages/db` (3 testes: isolamento entre agências, `@@unique` campanha+funcionário, prova estrutural de que `EnpsResponse` não carrega identificador de quem respondeu). Suite completa: 9 (Sidebar) + 49 (`packages/db`) = 58/58 passando.
- **Cohort e Reativações** (seção 32.2 e 32.3 do manual, sexta fatia da Fase 2, fecha a seção 32 inteira) — dois itens de nav que já existiam (`/clientes/reativacoes` como `comingSoon: true`; `/clientes/cohort` é novo).
